# Build Tableau → Power BI PBIP

Produces a PBIP project — `.pbip` + `<name>.SemanticModel/` (TMDL) + `<name>.Report/` (PBIR).

> **Corpus-agnostic.** This skill has no built-in knowledge of any particular workbook,
> dashboard or field. Every path is an argument. Measured figures quoted below are
> provenance from the reference corpus, not thresholds or expectations for your input —
> see [`docs/reference-corpus.md`](../../../docs/reference-corpus.md).

## Run

```bash
python3 scripts/build_pbip.py <input.twbx | folder-of-twbx> --out <folder> [options]
```

| Option | Meaning |
|---|---|
| `--out` | required; one project folder is created per workbook |
| `--tds <dir>` | folder of sibling `.tds`/`.tdsx` published datasources. Needed for any workbook whose connection is `sqlproxy` — without it the workbook has no schema to extract |
| `--partitions stub` | **default.** Typed empty `Table.FromRows`. Opens in Desktop, validates every DAX expression against a real schema, asks for no credentials |
| `--partitions native` | real M for the mapped connection classes; unmapped classes still fall back to stub and are listed in `RESIDUE.md` |
| `--clean` | delete each output project first |

Exit code is non-zero if any pre-flight assertion fails.

**Output location convention:** `--out` a folder alongside `inventory-tableau-assets`'s output for
the same corpus/run, not a top-level `output/` directory — e.g.
`docs/output/<corpus>/<run>/pbip_out`, a sibling of that run's `inventory_out`. Both skills' output
should live under one run folder so a corpus's full artifact set (census + build) is in one place.

## The rule that governs everything

> **Fail closed.** Anything not cleanly convertible is declined with a reason and reported as
> residue. It is never approximated, never partially emitted, never guessed.

A silently-wrong measure is far worse than a missing one: the model loads, the visual renders, and
someone reads a number that is quietly incorrect. A *missing* measure is visible in `RESIDUE.md`
and as a gap in `COVERAGE.md`.

### Folders → `displayFolder`

Tableau's Data-pane `<folders-common>` folders have a real Power BI equivalent — TMDL's
`displayFolder` property on a `column`/`measure` groups fields in the Fields pane exactly the way
a Tableau folder groups them in the Data pane, nested folders included (`\`-joined). Every calc,
schema column, group and bin carries its source folder (if any) from `extract.py`'s
`parse_folders()` through to `tmdl.py`'s `_calc_column`/`_measure`/`_column` emitters.

**Not yet re-measured against the full 6-workbook run the table above comes from** — only 2 of
those 6 use folders at all (`grep -c "<folder name=" <workbook>.twb`), and this feature was added
after that run:

| Workbook | Folders | Field identities in source | Emitted with `displayFolder` |
|---|---|---|---|
| WorkbookD | 5 | 42 | 15 (36%) |
| WorkbookC | 1 | 71 | 28 (39%) |

The shortfall here is **not** an independent gap — it tracks the calculated-field ceiling above
almost exactly (a folder-item pointing at a calc this build declined has no TMDL object to attach
`displayFolder` to; nothing new is lost). `check_display_folder_syntax` (`tools/pbip_rules/checks.py`,
rule SM-NAME-07) validates every emitted path has no leading/trailing/doubled separator; both
rebuilds above pass `tools/pbip_lint.py --schemas` clean.

Of the 728 views, **348 (47.8%) had their `visualType` decided by a rule**; the other 380 went to
the review list in `RESIDUE.md` and were emitted as `tableEx`. 480 field-well projections were
bound.

condition shape makes Desktop refuse the **entire project**, not just that visual, so 40 filters are
not worth the risk of guessing.

## Why calculated fields are 67.4% — and the rest is mostly not a missing syntax

These four are now translated deterministically, taking 60.8% → 67.4% with **zero LLM calls**:

| Tableau | DAX | Note |
|---|---|---|
| `{ FIXED [a],[b] : SUM([x]) }` | `CALCULATE(SUM(…), ALLEXCEPT('T', 'T'[a], 'T'[b]))` | `ALLEXCEPT` *is* what FIXED means. `{FIXED : …}` degenerates to `ALL` |
| `ATTR([col])` | `SELECTEDVALUE([col], "*")` | exact — value when one, `*` otherwise |
| `DATENAME('month', d)` | `FORMAT(d, "mmmm")` | `day`/`quarter`/`hour` go via `DAY()`/`MONTH()`/`HOUR()`: `dd` zero-pads where Tableau does not, and VBA `h` is 12-hour |
| `STR(x)` | `(x & "")` | coerces any non-date value; **a date argument is declined** because Tableau emits ISO and DAX coercion is locale-dependent |

`INCLUDE` and `EXCLUDE` stay with the LLM tier: they are relative to the view's own dimensions,
which a semantic model does not have at build time.

What remains, by cause:

| Cause | Does DAX have the syntax? |
|---|---|
| **Cascade** — depends on another declined calc | yes; blocked only by its dependency |
| **Table calculations** (`WINDOW_*`, `LOOKUP`, `INDEX`, `RANK`) | **no** — see below |
| **Dangling in the Tableau source itself** (15) | n/a — referenced but defined nowhere in the workbook |
| `REGEXP_MATCH()` | **no** — DAX has no regular-expression function |
| `DATEPARSE`, `SPLIT`, `COUNTD(<expr>)`, arity mismatches | mostly yes, with care |

### Table calculations cannot be translated at all, and not for want of trying

Their meaning is not in the formula. `[X] / TOTAL([X])` depends on Tableau's "Compute Using"
setting, stored in a `<table-calc>` element attached to the field's placement **on a shelf**. Three
valid DAX readings (`ALL`, `ALL(col)`, `ALLEXCEPT`) give three different numbers.

Measured on the reference corpus: of 34 table calcs, **only 4 had a discoverable spec, and 30 had
none at all** — one is defined and never placed on a shelf, so the disambiguating information is absent from
the file entirely.

Worse, the spec is **per placement**. `LOOKUP([X], -12)` appears in two worksheets whose Rows
shelves differ (3 dimensions vs 1), so it means two different things — while a DAX measure has
exactly one definition. So even the 4 with specs cannot be mechanically translated. This is a
**human** decision, and specifically **not** an LLM one: an LLM asked to translate a formula whose
meaning is not in the file will produce one confidently, and the result loads, renders and shows a
plausible wrong number.

**Measured ceiling for function-level mapping: 68.3%, not 100%.** Reason counts mislead on their own,
because a declined calc often has **several** blockers and only the first is reported — mapping
`ATTR` and `DATENAME`, 36 calcs by reason count, recovered exactly **1** before the LOD and `STR`
work landed alongside them.

### Two numbers here are lower than an earlier estimate, and the earlier one was wrong

**Calculated fields: 67.4%, and an earlier 83.7% claim was wrong.** That earlier figure came from a test
harness whose resolver returned a reference for *every* field name it was asked about. So a formula
referencing a calc that had itself been declined counted as a success — it would have emitted DAX
pointing at a model object that does not exist. Once references must resolve to objects actually
written to TMDL, the honest figure was 60.8%; the four mappings above then took it to 67.4%. The parser did not get worse; the
measurement got honest.

**Views typed by a rule: 47.8%.** An earlier run reported ~1731 "decided" visuals against a
728-view denominator — 290% "coverage", because the numerator was also counting filter, text and
image containers. Those are now counted on their own line.

## What each stage does

| Script | Stage | Role |
|---|---|---|
| `extract.py` | S0+S1 | unpack, resolve sibling `.tds`, typed IR |
| `names.py` | S2 | Name Authority — allocates every PBI identifier before either builder runs |
| `dax.py` | S3 D+ | Tableau formula → DAX, recursive descent, fails closed |
| `tmdl.py` | S3 | TMDL writer + the decline-cascade fixpoint |
| `pbir.py` | S4 | PBIR writer + the mark → `visualType` rule table |
| `build_pbip.py` | S5 | orchestrate, assemble, pre-flight, report |

Each has a self-test: `python3 scripts/<name>.py`.

### `names.py` — the failure it exists to prevent

PBIR binds to model objects purely by **name**, no ID indirection. In a prior build the model
emitted a table `Param Show as` while the report referenced `Parameters.Show as`; every
parameter-bound visual dangled. So one convention lives in one place and both builders read it:

```
table    'Param <Caption>'
column   Value
measure  '<Caption> Selected'  = SELECTEDVALUE('Param <Caption>'[Value])
```

It also tracks **allocation vs emission** separately, which is not a distinction I expected to
need. A calc is allocated a name up front, then the parser may decline it — leaving an allocated
name with no object behind it. The report resolver requires `emitted_only`.

### `tmdl.py` — why resolution iterates

Whether calc A can be translated depends on whether calc B, which A references, survived. B is
translated later in the same pass, so one pass emits A with a reference to a B that is then
declined. `resolve_calcs()` iterates until the declined set stops growing. On the reference corpus
that took up to 5 iterations, and `RESIDUE.md` distinguishes a cascade (`depends on 'X', which was itself
declined — translating that one calc would also recover this`) from a genuinely missing field,
because those need opposite fixes.

### `pbir.py` — why 52% of views are undecided

62% of corpus worksheets carry mark class `Automatic`, which is **not a value in the file** —
Tableau resolves it at render time from the shelf field types. So the rule table keys on
(mark, shelf shape), and where the shape is ambiguous no rule fires. Those views are emitted as
`tableEx` and listed for review. `tableEx` is deliberate: a table shows every field that was on the
shelves and is obviously unfinished, whereas a plausible-looking `barChart` would hide the fact
that nothing decided it.

Each of these was invisible to reading the code, and each was found by running it against real
workbooks. They are recorded because they show *what kind* of defect survives code review in this
domain — the specific workbook names are incidental provenance:

| Bug | Consequence had it shipped |

| Parameters indexed by caption, formulas reference internal name | 18 of WorkbookD's 79 calcs declined for parameters that were in the model all along |

| `DISTINCTCOUNT(IF(...))` | DAX aggregates take a **column**, not an expression — fails at load. Now rewritten to the `X` iterator where one table is unambiguous, declined otherwise |
| Two calcs sharing a caption collapsed to one authority key | **6 duplicate members** in one table — TOM forbids it, model would not load. The authority now keys on Tableau's internal name |

## Known limits

- **Not opened in Power BI Desktop by this skill itself.** Desktop requires Windows; this is built
  on macOS, so every claim above is structural — files exist, TMDL is tab-indented, every PBIR
  field reference resolves to an object the emitted TMDL actually declares. It HAS been opened in
  real Desktop by a real user twice, on real generated output, and both times found a hard failure
  no structural check here had an assertion for at the time (the case-insensitive name collision
  two rows up, and the filter-literal type mismatch above). Both are now fixed with a `preflight()`
  backstop. That pattern — a structural check passes, Desktop still rejects it, the gap gets closed
  — is exactly why "someone opens it in Desktop" remains the single most valuable check, at any
  frequency greater than "found by accident, twice."
- **Syntactic validity is not numerical equivalence.** 67.4% means the DAX parses and its
  references resolve. Whether a translated measure returns what Tableau returned needs a data-level
  QA pass against both systems. Nothing here establishes that.
- **Field-well shape is schema-doc only.** No visual in `docs/examples/` carries a `queryState`, so
  the projection shape is unverified against a real Desktop file. 480 projections depend on it.
- **The join path is exercised only by the synthetic probe.** The reference corpus has 0 key-based
  joins, so `tests/Synthetic Coverage Probe.twb` is the only thing covering it — see
  `tests/README.md`. It exists because relying on real input alone silently dropped a real join,
  which is the general lesson: a corpus tests what it happens to contain.
- **`relationships.tmdl` came out empty on the reference corpus, and that was correct.** The only
  relationships that input declared were two `1 = 1` cross joins, which no Power BI relationship can
  express, so they were reported as `GAP`. A federated Tableau datasource is also extracted as one
  table, so its internal joins have no second table to relate to — also reported, not silently
  dropped. An empty `relationships.tmdl` is therefore not automatically a defect; read `RESIDUE.md`
  to see which case yours is. **The key-based join path remains unexercised by real input.**
- **LLM and human tiers are not wired.** Everything routed to them lands in residue, reported per
  object with a reason rather than emitted as placeholders — 215 calcs on the reference corpus. See the cause table above for what each tier owns.
- **15 calcs reference fields defined nowhere in their own workbook.** That is a finding about the
  source, not a translation failure — those calcs are already broken in Tableau.
- **`--partitions native` M is unverified.** Only `Sql.Database` appears in the schema reference;
  the rest of the connector map is from the M library, not from anything checked here. That is why
  `stub` is the default.

## Future recommendation: a typed-expression layer in `dax.py`

Three real Desktop bugs this session (calculated column referencing a measure; a promoted measure
with no row context for its bare column references; Tableau's `+` mistranslated to DAX's always-
arithmetic `+` instead of `&`) were all **syntactically valid DAX that is semantically wrong** —
none would have been caught by a stricter grammar or a DAX "railroad diagram", since every one
parsed fine and failed only at model-load or query time. Each was fixed with a narrow, literal- or
context-anchored heuristic scoped to the exact evidence found (a string literal touching `+`; a
calc promoted to measure with no aggregate function of its own), not a general type system.

The systematic version of this fix: have every sub-expression carry a coarse type/context tag
(`numeric`/`text`/`date`/`boolean`, plus "am I currently inside row context") through the
recursive descent in `dax.py`'s `Parser`, instead of pattern-matching on the already-translated
DAX string after the fact. That would turn "is this `+` concatenation or addition" and "does this
column reference need `SELECTEDVALUE`" into principled lookups against propagated type/context
info, catching this whole bug family before shipping rather than one Desktop error at a time. It
is a genuine refactor — `Parser`'s methods currently return plain DAX strings; they would need to
return `(dax_text, type_info)` throughout — not a quick patch, and there is no local DAX/Tabular
engine available in this environment to validate against directly, so type tracking is the
practical ceiling here, not full semantic execution.

**Decision (2026-08-26): not doing this now.** Continuing case-by-case — fix the specific bug when
a real Desktop error reports it, same as the three above — until this class of error recurs enough
to justify the refactor's cost. Revisit if it does.
